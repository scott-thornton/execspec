# Executable Specification System - Specification

This document is normative for execspec v0.1.

## 1. What execspec is

execspec is a system in which a developer authors a **portable behavioral
specification** in TypeScript, the specification compiles to a **canonical
semantic intermediate representation (IR)**, implementation targets (v0.1:
Swift) are **generated strictly from the IR**, and a harness verifies any
conforming implementation through a **language-neutral process protocol**.

The one-sentence invariant:

> TypeScript owns authoring, the semantic IR owns meaning, Swift is only an
> implementation target.

## 2. Architecture

```text
TypeScript DSL source
        ↓  (build)
AuthoringGraph
        ↓  (compile: validate, lower, normalize)
SemanticIR (canonical, language-neutral)
        ↓  (generate)                    ↓ (interpret)
generated Swift types/protocol/       scenario interpreter (harness)
codecs/dispatcher                            ↓
handwritten Swift implementation  ←  NDJSON protocol over stdin/stdout
```

Roles:

- **`@execspec/core`** owns semantic types, semantic values, validation,
  equality, the IR types, IR validation, canonical JSON serialization, and
  the specification digest.
- **`@execspec/dsl`** constructs an AuthoringGraph. It contains no
  compilation logic.
- **`@execspec/compiler`** validates and normalizes the AuthoringGraph into
  a `SemanticIRDocument` plus digest.
- **`@execspec/swift-generator`** consumes only `SemanticIRDocument`. It
  must never inspect TypeScript source or the authoring graph.
- **`@execspec/harness`** executes Scenario IR against a spawned
  implementation-host process. It depends only on `@execspec/core`.
- **`@execspec/cli`** wires the commands `compile`, `generate swift`, and
  `test`.

## 3. Global constraints (normative)

1. TypeScript owns authoring, not semantics.
2. Canonical Semantic IR owns portable meaning.
3. Swift is only an implementation target.
4. Target generators consume Semantic IR and MUST NOT inspect TypeScript
   source.
5. The IR contains no JavaScript, closures, source-code strings, Swift
   concepts, or executable host-language code.
6. All normative scenarios compile into IR.
7. Domain failures are values in operation outputs.
8. Protocol, process, decoding, crash, and timeout failures are
   implementation/harness failures and are never domain values.
9. A fresh implementation-host process is created for every scenario.
10. v0.1 has no reset operation, no callbacks, no streaming, no
    concurrency specification, no property-based testing, no arbitrary
    semantic predicates.
11. v0.2 supports: `unit`, `boolean`, `int64`, `float64`, `string`,
    `bytes`, optional struct fields, `list`, `map` (string or int64
    keys), named struct, named enum, named tagged union. The wire and
    equality rules for every kind are normative in
    `docs/semantic-model.md`.
12. `optional` is permitted only on struct fields in v0.1.
13. Struct and union declarations are nominal. Anonymous structs, enums,
    and unions are prohibited.
14. Operations accept exactly one semantic input value and return exactly
    one semantic output value.
15. Names must be unique in their namespace; `$`-prefixed user names are
    prohibited (`$` is reserved for wire-level encodings).
16. Source ordering does not define semantics; canonical IR serialization
    provides deterministic ordering.
17. SHA-256 of canonical semantic IR is the specification digest.
    Source-location metadata is not part of the digest.
18. All generated files begin with `// Generated by execspec. DO NOT EDIT.`
    and are never manually edited.
19. The harness validates outgoing inputs and incoming outputs. Invalid
    output is a conformance failure.
20. stdout of an implementation host is protocol-only; diagnostics go to
    stderr.
21. One protocol message occupies exactly one UTF-8 line; the line limit
    is 16 MiB.
22. Operation timeout is 5 seconds by default, configurable through the
    CLI only.
23. Protocol version is integer `1`. IR version is integer `1`.
    Version-change policy: `docs/compatibility.md`.
24. The reference systems are a stateful key/value store and an
    ordering domain, each implemented in both targets (Swift,
    TypeScript).

## 4. Naming rules

| Namespace        | Grammar                                  | Example          |
| ---------------- | ---------------------------------------- | ---------------- |
| Type ID          | `^[A-Z][A-Za-z0-9]*$`                    | `PutRequest`     |
| Operation ID     | `^[a-z][a-z0-9]*(\.[a-z][a-z0-9-]*)+$`   | `kv.put`         |
| Scenario ID      | `^[a-z][a-z0-9]*(\.[a-z][a-z0-9-]*)+$`   | `kv.get.missing` |
| Member name      | `^[a-z][A-Za-z0-9]*$`                    | `key`            |

Member names cover struct field names, enum case names, and union case
names. Operation ID segments may additionally contain `-` (kebab words).

## 5. Scenarios

A scenario is a **declarative program**: an ordered list of steps, each
either:

- `call` - invoke an operation with an input value expression and bind the
  output under a binding name.
- `expectEqual` - compare two value expressions for portable semantic
  equality.

Value expressions are `literal`, `binding` (a previous call binding), or
`field` (struct field or union payload traversal of another expression).
Forward binding references are compile errors. No loops, branches,
parallelism, or arbitrary expressions exist in v0.1.

## 6. Definition of done

The project is complete only when the complete end-to-end KV example passes
without test-specific logic in the generated host, all gates
(`npm run check`) pass from a clean checkout, deliberately broken
implementations fail, and stale hosts fail the digest handshake before any
operation is dispatched. See `docs/autonomous-loop.md` for the completion
protocol.

## 7. Deferred scope

Unsigned integers, timestamps, durations, sets, tuples, recursive types,
refinements, preconditions/postconditions, property-based testing,
fuzzing, callbacks, streaming, cancellation, concurrency semantics,
virtual clocks, randomness, network/filesystem capabilities, snapshot
testing, HTTP/socket/gRPC transports, FFI, and additional target
backends beyond Swift and TypeScript are explicitly excluded. They are
not missing work; they are excluded scope - see `docs/compatibility.md`
for the rules governing additions.
